# 技术决策记录

## 001：原生 Apple 技术栈

状态：已采用

使用 SwiftUI 构建 iPhone App，领域规则放在本地 Swift Package 中。应用数据后续使用 SwiftData，健康数据使用 HealthKit。第一阶段不引入社区、登录系统或 CloudKit。

## 002：规则优先于模型输出

状态：已采用

营养标签识别和多模态模型只负责提取候选字段。维生素 A、清真状态、数据完整度和营养评分由版本化本地规则决定。明确违规证据优先于信息完整度。

## 003：先支持模拟器，再处理真机签名

状态：已采用

先用无签名模拟器构建推进工程和规则；HealthKit 权限与真机行为在开发者账号配置完成后验证。目前已用 Personal Team 完成真机构建，但免费签名仍有 7 天有效期。

## 004：拍照估算餐进入 v0.1

状态：已采用

餐厅堂食、食堂和朋友家用餐无法稳定称重。如果这些天被排除在完整日之外，滚动平均会持续低估实际摄入。因此，v0.1 增加拍照估算餐，并把开发周期调整为 7 周开发加 2 周个人试用。

多模态模型只生成菜品组成、烹饪方式、模板映射、低中高份量和置信度。营养值仍由本地数据库按克数计算。用户可以用小中大份、碗数、盘面比例或多人分食比例修正，并单独调整看不见的油和酱汁。

记录覆盖完整度和估算精度分开保存。当天每一餐都已记录时，即使包含拍照估算餐，也可以作为完整日进入滚动平均；界面同时显示营养区间和证据等级。能够称重时，App 保存照片估值与实际重量的成对数据，累计到足够样本后再启用有边界的个人校准。

## 005：正式产品名称

状态：已采用

App 主屏幕显示名称使用“食衡”，英文产品名使用 `ShiHeng`，正式 Bundle ID 使用 `com.ning6y6.ShiHeng`。为降低 Xcode 工程重命名风险，内部 Target、Scheme 和源码目录继续使用 `FoodDecisionAssistant`；构建产物为 `ShiHeng.app`。

## 006：餐食分项保存营养快照

状态：已采用

“记录一餐”的每个分项保存 FoodItem ID、名称、克重、单位、顺序和当时计算出的营养快照。今后更新种子数据或切换数据源时，不会静默改写历史餐食。

首批个人食材库使用英国政府发布的 [CoFID 2021](https://www.gov.uk/government/publications/composition-of-foods-integrated-dataset-cofid) 每 100 克数据、固定 UUID 和幂等导入。来源缺失的纤维保留为未知，不伪造为 0；盐按 CoFID 钠值乘以 2.5 换算。

## 007：默认简洁，高级信息渐进展开

状态：已采用

日常餐食记录的主路径只强调餐食名称、食物和份量。记录方式、证据等级和覆盖状态保留为可展开的高级项；营养来源默认只显示数据库名称，不在高频界面堆叠内部编号。

首页后续改版使用圆形进度图表达当日热量：圆环随摄入增长，达标时闭合，超出后按程度改变颜色。颜色阈值必须作为可测试的本地配置，不由 UI 临时判断。完整视觉重构在餐食编辑/删除和快速模板稳定后进行，但不等到所有 AI 功能完成才开始。

## 008：原生 UI 优先，Skills 按阶段加载

状态：已采用

当前开发只安装 SwiftUI、SwiftData、Swift Testing 和 Swift Concurrency 四个 MIT skills。Vision、HealthKit、Charts 和 AlarmKit 等专项 skill 到对应开发切片再安装，不并行堆叠多套同类建议。

UI 优先使用 SwiftUI、Swift Charts、SF Symbols、系统触感和系统 Liquid Glass 行为。Liquid Glass 只用于浮层交互控件，营养数字与硬约束结论不放在玻璃材质上；不为点缀动画引入第三方运行时依赖。

热量圆环采用版本化的本地规则：目标内为绿色，超出目标但不超过 10% 为琥珀色，超过 10% 为红色。任何颜色状态都必须同时提供图标和文字。
