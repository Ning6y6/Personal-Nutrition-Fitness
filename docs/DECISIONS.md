# 技术决策记录

## 001：原生 Apple 技术栈

状态：已采用

使用SwiftUI构建iPhone App，领域规则放在本地Swift Package中。应用数据已使用SwiftData；HealthKit尚未接入。第一阶段不引入社区、登录系统或CloudKit。

## 002：规则优先于模型输出

状态：已采用

营养标签识别和多模态模型只负责提取候选字段。维生素 A、清真状态、数据完整度和营养评分由版本化本地规则决定。明确违规证据优先于信息完整度。

## 003：先支持模拟器，再处理真机签名

状态：已采用

先用无签名模拟器构建推进工程和规则；HealthKit 权限与真机行为在开发者账号配置完成后验证。目前已用 Personal Team 完成真机构建，但免费签名仍有 7 天有效期。

## 004：拍照估算餐进入 v0.1

状态：已采用

餐厅堂食、食堂和朋友家用餐无法稳定称重。如果这些天被排除在完整日之外，滚动平均会持续低估实际摄入。因此v0.1增加拍照估算餐。原7周开发加2周个人试用是计划A的历史估算，不是当前完工承诺；可靠性门禁通过后重估排期。

多模态模型只生成菜品组成、烹饪方式、模板映射、低中高份量和置信度。营养值仍由本地数据库按克数计算。用户可以用小中大份、碗数、盘面比例或多人分食比例修正，并单独调整看不见的油和酱汁。

记录覆盖完整度和估算精度分开保存。完整日需要每餐已记并有用户日级确认，包含已确认C估算餐仍可纳入；D草稿不进入正式统计。日级确认和滚动平均尚未实现。能够称重时保存照片估值与实际重量成对数据，累计足够样本后再启用有边界的个人校准。

## 005：正式产品名称

状态：已采用

App 主屏幕显示名称使用“食衡”，英文产品名使用 `ShiHeng`，正式 Bundle ID 使用 `com.ning6y6.ShiHeng`。为降低 Xcode 工程重命名风险，内部 Target、Scheme 和源码目录继续使用 `FoodDecisionAssistant`；构建产物为 `ShiHeng.app`。

## 006：餐食分项保存营养快照

状态：已采用

“记录一餐”的每个分项保存 FoodItem ID、名称、克重、单位、顺序和当时计算出的营养快照。今后更新种子数据或切换数据源时，不会静默改写历史餐食。

首批个人食材库使用英国政府发布的 [CoFID 2021](https://www.gov.uk/government/publications/composition-of-foods-integrated-dataset-cofid) 每 100 克数据、固定 UUID 和幂等导入。来源缺失的纤维保留为未知，不伪造为 0；盐按 CoFID 钠值乘以 2.5 换算。

## 007：默认简洁，高级信息渐进展开

状态：已采用

日常餐食记录的主路径只强调餐食名称、食物和份量。记录方式、证据等级和覆盖状态保留为可展开的高级项；营养来源默认只显示数据库名称，不在高频界面堆叠内部编号。

首页基础热量圆环已经实现：随摄入增长，达标时闭合，超出后按程度改变颜色。S2集中配置可测试的显示阈值，不由UI临时判断；全面视觉重构及四栏导航不混入S0–S2，等待对应切片批准。

## 008：原生 UI 优先，Skills 按阶段加载

状态：已采用

当前开发只安装 SwiftUI、SwiftData、Swift Testing 和 Swift Concurrency 四个 MIT skills。Vision、HealthKit、Charts 和 AlarmKit 等专项 skill 到对应开发切片再安装，不并行堆叠多套同类建议。

UI 优先使用 SwiftUI、Swift Charts、SF Symbols、系统触感和系统 Liquid Glass 行为。Liquid Glass 只用于浮层交互控件，营养数字与硬约束结论不放在玻璃材质上；不为点缀动画引入第三方运行时依赖。

热量圆环采用版本化的本地规则：目标内为绿色，超出目标但不超过 10% 为琥珀色，超过 10% 为红色。任何颜色状态都必须同时提供图标和文字。

## 009：四栏系统主导航

状态：已规划，尚未实现

App 的长期根结构采用“今日、扫描、日历、设置”四栏系统 `TabView`。每个 Tab 使用独立 `NavigationStack`，选择状态由 `AppTab` 枚举表达。使用系统 Tab Bar、SF Symbols 和 iOS 26 自带的 Liquid Glass 行为，不复制参考 App 的自定义悬浮底栏。

“日历”直接聚合历史餐食的时间和营养快照，不建立重复的每日汇总表；“设置”先承接每日目标；“扫描”只提供 P2 的固定入口，不允许未实现的占位页伪装成可用扫描流程。

## 010：可靠性加固优先于新业务

状态：已采用，2026-10-04用户批准

采用OPTIMIZATION_EXECUTION_PLAN作为当前执行清单：S0保存模板基线并统一文档，S1完成可恢复备份、实际旧库识别和迁移边界，之后才实施S2领域校验、目标保存、提示策略与未知营养。每次只交付一个OPT任务；S3–S5需后续批准，不因依赖代码相似而提前实现。

真机已开始记录，不能继续用“尚未发布、清数据重试”代替兼容策略。先保留仓库外的受保护旧库，测试只在副本或合成文件库进行；不能仅凭Schema名称V1推断结构兼容。实际部署结构尚未核实或恢复门禁未通过时，不进入S2，不改持久化Schema或严格旧数据读取。

ROADMAP是当前路线，DECISIONS记录决策，EXECUTION_STATUS记录实际证据；旧Word计划仅为历史快照。导航整体改版不混入S0–S2。

## 011：本地使用范围与独立任务分支

状态：已采用，2026-10-04用户批准

目前支持用户及一两位朋友各自本机使用，不等于共享数据、云同步或多人后台。保留本地唯一约束，不引入CloudKit或Supabase。

新功能使用feat/，缺陷使用fix/，不改变行为的重构使用refactor/；文档和独立测试使用docs/、test/。每个任务独立验证并提交，已授权推送到GitHub；优先快进整合，不强推、不重写已有历史。真实健康数据、旧库、Key与签名材料不得提交。

## 012：冻结已确认本地结构，恢复不覆盖原库

状态：已采用，OPT-08自动化验收通过；人工真机恢复交互待验

真实部署库经磁盘哈希确认是12实体V1。冻结字段、关系、唯一约束和删除规则；未来需要保留数据的存储变更建立新版本和显式迁移。早期同名9/10实体V1没有实际部署样本，未知哈希保留并拒绝自动迁移，不凭版本名猜测兼容。

JSON先恢复到独立私有库，关闭重开核对全部原始记录与关系，经二次确认才原子发布选择标记并替换App容器。原库保留，不合并、不清洗旧值；打开失败提供重试及已有备份恢复，不能承诺打不开的库仍可导出。诊断不包含个人记录。S1门禁已通过，S2只改变领域边界和UI逻辑，不改变冻结Schema。

## 013：目标由用户明确确认，保存独立于页面草稿

状态：已采用，OPT-04自动化验收通过；真机UI待验

首次目标表单不提供可直接保存的预填示例。已有值精确载入，修改或保存均需主动确认；可选留空保留未设置，明确0保留已知0。完整文本解析与领域校验位于Core。显示策略不生成医疗阈值，也不表示目标来源已经获得临床确认。

目标保存使用独立关闭autosave的上下文，失败只回滚本事务，不能为了刷新而保存或回滚共享页面草稿。保存成功后首页使用新读取上下文取得已提交值。S2仍编辑既有目标，不增加持久化来源/确认字段或版本；目标历史与生效时间契约留在S3，未提前实现。

## 014：按目标语义显示，不用颜色代替判断

状态：已采用，OPT-05自动化验收通过；真机UI待验

蛋白质、纤维采用minimum；热量、碳水、脂肪采用budget；饱和脂肪采用maximum。达最低目标不报上限超量，也不表示越多越好。预算未满显示“预算剩余”而非要求吃满；上限到达明确“尚未超出”。所有状态、差额和进度由Core产生，App同一值适配器同时映射文字、图标和颜色。

NutritionDisplayPolicy.v1集中保存80%上限预警和超过预算10%的明显超出参考线，构造与解码共用验证。预算超出不超过10%为琥珀，超过10%为红；上限80%起为琥珀，超过100%为红。这是显示策略，不是系统设定的医疗目标。明确0、未设置、未知摄入和非法输入分别处理；非法值不夹成0后显示绿色。能量目标仍须严格大于0。显示舍入不能改变分类，微小正超出用“不足0.1”保留其非零含义。

## 015：未知纤维保留，小计不冒充总量

状态：已采用，OPT-06自动化验收通过；真机UI待验

源数据和历史快照的nil继续表示未知。派生FibreIntakeSummary从各个合法正式餐食的分项快照展开，保留已知小计与未知数量；不根据肉类常识补0、不跨生熟状态拼接来源，也不读取新版源食品去更改旧餐。NutrientValues.sum的未知语义不变。

部分已知显示已知下界及未知分项，全部未知和无分项分别显示；明确0只有在完整数据下才是精确0。小计不能作为精确总量或剩余缺口，不赋予达标颜色；下界舍入不向上夸大。该模型的isComplete仅表示所提供分项的纤维数据齐全，不是整日餐食记录覆盖确认，不能用于跳过S3的日级确认门禁。

## 016：路径校验以系统容器为边界，不遍历容器外祖先

状态：2026-10-04用户批准，自动化验证通过；修复后真机启动待验

生产可信边界取系统`NSHomeDirectory`，不能从导入文件或候选路径推断共同祖先。只逐级读取边界自身与内部路径属性；测试和开发探针显式提供独有隔离根。系统`/var`和`/tmp`的前缀别名只作组件归一，不整体解析用户候选路径来掩盖内部链接。

原始`.`/`..`、兄弟前缀越界、内部符号链接及非目录祖先继续拒绝；权限或属性读取失败与不安全路径区分，但同样阻止开库。缺失的内部子路径可用于首次安装，缺失的可信根不可接受。不能用“原始路径等于Foundation标准化路径”判断安全：已有系统别名可能改变规范化拼写。恢复固定布局按同一边界下的相对组件核对。

不改变默认库位置、选择文件契约或冻结V1。不得以卸载、清库或禁用全部路径检查解决真机启动问题；模拟器和Mac副本通过不替代真机启动、原记录可见和重启验证。
