# 食衡优化执行清单

- 版本：批准版 1.0
- 整理日期：2026-10-04
- 状态：2026-10-04 用户批准 S0–S2，按任务顺序执行；S3–S5待后续批准
- 适用项目：食衡 ShiHeng，原生 iOS，自用或一两位朋友各自本机使用，本地优先

本清单合并本机架构审计与用户提供的外部 AI 静态审查。目标是先保证既有记录可靠、可恢复、易录入，再继续原定的自定义食品与个人菜谱批次。保留 SwiftUI、SwiftData、FoodDecisionCore；不重建 Xcode 工程，不提前引入后端。

用户已批准本清单作为正式路线修订依据，并授权现有功能基线及S0–S2改动的Git提交、GitHub推送。未实施事项仍保持未完成；没有授权云同步、账号购买或S3–S5实现。

## 当前基线和证据范围

- 当前已提交基线：`240356d feat: add meal history management`。
- 制作本清单前，工作区为 10 个修改文件、7 个新增文件，主要包含最近吃过与个人模板业务。此数量不包含本清单。
- 上一轮本机审计实际执行了 Core 测试、iOS 模拟器测试和 App 构建，结果为 28/28、13/13、构建成功。本轮只制作计划，不重新宣称增加了测试或通过了新验收。
- 本机额外诊断复现了无限克数被接受、MealLog 不校验入口、补剂子串误匹配及评分器 NaN 崩溃。评分和补剂规则目前未接入正式扫描界面。
- 模板同 UUID 删除重建，在临时 macOS SwiftData 文件库连续编辑和重新打开时正常。仍需 iOS 对应路径测试，但不列为已证实的数据丢失。
- 外部 AI 没有 Xcode，其运行、迁移和性能判断属于静态风险分析，不能替代本机测试。其“第一阶段约完成三成”没有固定需求分母和权重，不作为项目完成率。
- 尚未完成的真机计时、内存、帧率、旧库迁移和恢复验收仍标为待验证。

## 执行优先级和开发边界

- P0：保护已有数据、阻止非法正式数据，恢复正常错误处理。进入持续日用前完成。
- P1：修复业务语义和录入成本；其中集成功能项必须在对应功能启用前完成。
- P2：维护便利、目录整理和尚未需要的工具支持。
- S0至S5是执行阶段，与原路线图中的P0至P5功能阶段编号不同。
- 阶段不是一次巨型改动。同一时间只实施一个 OPT 任务，依赖满足后才进入下一任务；每次报告实际改动、验证结果和未完成项。
- DECISIONS、ROADMAP、EXECUTION_STATUS 和导航计划同步采用已批准执行顺序；旧 Word 保留历史快照，不再作为另一个当前执行源。
- 禁止自动清空真机数据库、重建工程、删改未知用户记录、添加第三方依赖、写入真实 API Key 或把个人健康备份提交到 Git。

## 后续功能启用前的强制门禁

这些事项记入后续切片，但不与OPT-03至06的当前修复同时接入真实网络、医疗判断或健康数据写入。

### 拍照确认和真实模型

- [ ] 明确`wholeDish`与`consumedPortion`两种份量输入，界面标清整盘/本人。个人食用150g配合50%分食仍为150g；整盘150g配合50%才为75g。已有记录按原来的整盘语义兼容。
- [ ] 区分称重修正与目测修正。目测手动输入不自动变成零宽度精确区间。
- [ ] 补红烧、炖煮、煎等中餐方式，但默认油范围标明来源或个人校准依据，不能由方式推断精确用油。
- [ ] 定义原料组合与成品菜模板是否包含油；隐藏油仅作明确增量或替换，避免双算。
- [ ] ConfirmPhotoMeal校验请求/Schema、食品映射、油项、份量与人工确认；本地计算低中高营养，关联正式C记录和来源版本；未确认D保留为草稿。
- [ ] 单次在途请求、可取消、明确超时、最多一次瞬时错误重试、日预算、版本化缓存和手动兜底。建议初始15秒超时，不把Fixture直接throw当作真实链路测试。
- [ ] 上传副本去除EXIF/GPS等无关元数据并回读验证；Keychain保管自用Key，日志无照片内容、医疗约束和Key。
- [ ] 校准集与验收集分离。20餐仅作为个人基线；整餐称重验证重量，已知原料/标签/用油验证热量。报告中心误差、覆盖率和区间宽度，不能靠无限扩大区间达标。

### 标签扫描和约束规则

- [ ] 成分/营养/营销文本分区，规范Unicode和换行，词边界与否定上下文回归；`Vitamin and mineral`不得变成明确违规证据。
- [ ] 规则返回真实证据片段、位置、规则ID、版本和来源；版本由已加载的本地配置提供，不接受OCR/模型自报版本；无法确定时保持待核对/咨询出口。
- [ ] 额外药物关键词经权威来源核实才进入规则集。记录约束的用户确认、生效范围与复核日期；日期到期不自动视为停药或取消禁忌。
- [ ] NutritionScoreEngine拒绝NaN/无限权重；补齐营养数值转分、必需字段门禁与已核对状态；可选纤维缺失策略单独定义，不给缺必需字段的商品正式绿灯。
- [ ] 清真状态独立表达；移除个人库不适用食品不等于商品已经通过清真认证。认证/配料证据与用户接受标准由本地规则处理。
- [ ] OCR字段准确率分别报告数值、单位和每100g/每份列；硬约束样本零错误绿灯。联网食物库只是来源与缓存，不是规则裁决者。

### HealthKit 同步实验

- [ ] 先在隔离测试餐完成六类营养保存、更新、删除与回查，再设计正式同步。诊断资料不含真实健康导出。
- [ ] 明确稳定syncIdentifier和严格递增syncVersion；当前编辑保留旧版本的问题在接入前解决。餐食实际内容改变才增加版本，无修改保存不增加；本地提交失败不增加版本。
- [ ] correlation和各sample分别验证残留/重复，不能假设删除correlation会级联删除所有sample。
- [ ] 同步采用可重试待处理记录与删除标记，本地餐食保存不被权限拒绝、离线或外部同步失败阻断。
- [ ] 真机验证权限、部分授权、重复编辑、删除后重试及失败恢复；不把Watch活动热量直接全部加回可吃额度。

同步标识和版本的更新行为依据 [Apple HKMetadataKeySyncIdentifier文档](https://developer.apple.com/documentation/healthkit/hkmetadatakeysyncidentifier)。当前尚无真实同步，不宣称已有重复写入事故。

### CloudKit 和后端

- [ ] 仅在明确需要跨设备/多账号/共享库/服务端AI代理后启动；当前不引入Supabase或CloudKit。
- [ ] 启用CloudKit前审查unique、默认值、可选关系、inverse、删除规则、业务去重和最终一致性；明确本地模型与云模型是否需要分离。
- [ ] 云同步不是备份替代品；失败不能影响本地录入，云端结构更改仍有迁移与恢复验收。

## 工程验证和交付规则

每个实现任务都要执行以下门禁，文档专用改动只需检查内容、链接与diff，不伪造代码验证结果。

1. 先增加对应回归测试，再做范围内实现。单位/集成测试使用Swift Testing，UI自动化使用XCTest。
2. 执行`swift test --package-path Packages/FoodDecisionCore`。
3. 使用FoodDecisionAssistant Scheme在可用iPhone模拟器上执行全部App单元测试，保存实际结果。
4. 执行`./scripts/build-ios.sh`。S0只保存并验证既有切片；S1持久化验证交付时补参数化测试入口，避免仅build或硬编码某一台模拟器，不把脚本改动混入模板基线提交。
5. 涉及存储的任务必须使用临时文件库和fresh context/重开container；加入保存失败、取消和复用计次原子性测试。
6. 涉及UI的任务完成焦点、保存、取消、错误状态及大字体验收；实机时间由用户完成或提供观察证据，不用构建成功代替。
7. 沙盒权限、缓存或模拟器服务错误与代码失败分别报告。报告实际测试数量，不预先承诺固定总数。
8. 只更新真实完成任务的状态；记录改动文件、数据兼容策略、测试结果、剩余问题和下一任务。
9. 每个任务可形成独立可回退提交；结构迁移后不得直接降级安装旧App作为数据回退方案，必须按已验证的备份恢复流程执行。
