日期：2026-10-30（Europe/London）。代码基线 `f091a58`，任务分支 `feat/personal-food-deletion`。

## 批准范围

用户批准仅在已保存个人卡编辑页底部增加“删除食物卡”，点击后确认并说明影响。保留现有表单布局、数据保护及内置食品；不删除历史餐食、模板、目标或其他记录，不清库，不增加归档、批量删除或新的食品数量模型。

## 实现边界

- 已有合法个人卡才有底部删除入口，新建卡没有。确认框直接挂在该按钮，先清除输入焦点，使用打开时的已存卡名称，不能把未保存改名误当删除目标。显式保留“取消”按钮。
- 确认文案说明：从“我的食物”和搜索中移除；原餐食及营养记录保留；含该卡的模板／最近餐食在复用时需重新选择；内置食品不受影响。若本页有未保存输入，同时说明这些修改将放弃。取消删除完整保留输入，包括非法数值。
- `PersonalFoodDeleteCommand` 每次重核 `PersonalFoodIdentity`：排除随包、旧种子和弃用内置 ID；要求合法个人来源、g 单位和完整数据。存在的目标需逐字段匹配编辑基线，不能删除已经改变的卡。
- 私有 ModelContext 关闭 autosave，只删除这一个食品行；不保存／回滚共享上下文。目标卡在共享上下文有待提交插入、编辑或删除时拒绝操作；无关食品、餐食、模板和目标草稿保留。
- 相同请求遇到目标已不存在时只核对刷新，不重复写入。区分未能确认提交与已删除但刷新失败；后一状态禁用保存，保留原请求，只允许核对删除结果。若同 ID 卡后来重新出现，核对重试拒绝再次删除。
- 成功返回“我的食物”，列表顶部提供删除状态提示；长列表保留原滚动位置，大字号时可能需向上查看提示。删除不改历史餐食分项的名称、克重和营养快照；旧餐改名称／时间仍保留快照，改重量仍按原快照缩放。

模板及最近餐食仍保留原食品 ID、名称和重量。复用时现有缺失食品提示和完整分项校验继续生效，不会自动去掉分项以便保存。模板没有独立营养快照；删卡后必须明确重选或移除该分项再记新餐。

备份允许食物 ID 指向已移除来源：它是值引用，不是级联关系。删除后生成的备份保留旧餐及模板并保持该食品缺失；删除前生成的旧备份仍包含这张卡，恢复旧备份会恢复其当时状态。删除不改写或删除已导出的备份文件。

不改 Core 规则、SwiftData 实体、冻结 V1、当前 V2、迁移或备份格式；不加依赖，不连接云服务，Bundle ID 保持 `com.ning6y6.ShiHeng`。只使用合成内存库、临时文件库和专用 QA 模拟器，不读取或删除真机记录。原工作区十个未提交路径独立保留，不混入提交。

3. **取消不丢输入**：进入该卡编辑，名称末尾加“未保存”，热量改成 `.`。下滑到底部，点删除。确认框必须显示原已存卡名称并说明影响；点“取消”后，未保存名称和 `.` 均保留，保存仍不可用。再点顶部取消→放弃修改，重新打开应仍是原名和 400 kcal。
